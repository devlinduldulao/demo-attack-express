# VaultPay on DaloyJS — the "after" build

The same demo API as [`../server/`](../server/) (Express 5), rebuilt on
[DaloyJS](https://daloyjs.dev) **with the same developer mistakes left in**.
Run the same attack script against both and compare what gets through.

This build is local-only. It has no Cloudflare / Vercel deploy config.

## Run it

```bash
# repo root
npm run install:all

npm run compare                    # boots all three builds, attacks each, prints one table

npm run server:daloy               # http://localhost:4100 — scaffold defaults
npm run server:daloy:opt-in        # same, plus the first-party opt-in helpers
npm run server:daloy:weak-secret   # JWT_SECRET=supersecret123 → refuses to start
npm run attack:short:daloy         # attackv2.mjs against :4100 with --drama --projector
```

## Port rules

The comparison is only worth showing if it is fair, so the port follows five rules.
They are also at the top of [`app.js`](app.js).

1. **Same handler logic.** Handlers return the same objects the Express handlers
   return (`db.fullUser()` / `db.dumpUser()` rows and all). The seed data, the
   virtual file tree and the unsafe merge helper are imported from `../server/`.
2. **Scaffold setup only.** The app is configured the way `pnpm create daloy`
   scaffolds it: body limit, request timeout, `requestId()`, `secureHeaders()`,
   `rateLimit({ max: 120 })`, `.strict()` request schemas.
3. **One response schema.** DaloyJS will not register a route without a response
   contract. The developer wrote one public `User` schema — the same six fields
   as the Express app's own `publicUser()` helper — and reused it wherever a user
   is returned. **This is the one judgment call in the port.** A developer who
   typed `ssn` and `cardCvv` into that schema would leak them exactly as Express
   does. The debug endpoint shows the other side of this: its schema declares
   `jwtSecret`, so the secret is served.
4. **Opt-in helpers are a separate mode.** `requireRoles()`, `fetchGuard()`,
   `assertSafeRelativePath()`, `safeRedirect()` and `loginThrottle()` ship with
   DaloyJS but a developer has to know to call them. They are off by default and
   on with `DALOY_OPT_IN=1`, one line each.
5. **No ownership checks in either mode.** No framework knows who owns an order.

## The mistakes that are still in here

| Mistake | Where | Stopped by |
| --- | --- | --- |
| No auth hook on `/api/users`, `/api/users/:id`, `/api/search`, `/api/settings` | `app.js` | Nothing. The response schema only limits what leaks. |
| No ownership check on orders or on `PUT /api/users/:id` | `app.js` | Nothing. |
| Debug endpoint that prints the signing secret | `app.js` | Nothing. |
| No role check on `/api/admin/stats` | `app.js` | `requireRoles()` (opt-in) |
| File name joined onto a base directory | `app.js` | `assertSafeRelativePath()` (opt-in) |
| Server-side fetch of any URL | `app.js` | `fetchGuard()` (opt-in) |
| Redirect to any URL | `app.js` | `safeRedirect()` (opt-in) |
| Unlimited password guessing | `app.js` | `rateLimit()` slows it (scaffold); `loginThrottle()` stops it (opt-in) |
| Raw request body merged into the user row | `../server/merge.js` | `.strict()` request schema (scaffold) |
| Full database rows returned from handlers | `../server/db.js` | Response schema (required by the framework) |
| `supersecret123` as the HS256 key | — | Refused at construction in every environment |

## Two things to know before a live run

- **Rate limits are real.** The scaffold limit is 120 requests per minute per
  client and one attack run sends about 57. A third run inside the same minute
  starts getting `429`. Restart the server between rehearsals, or wait a minute.
- **Opt-in mode locks the attacker out.** `loginThrottle()` allows 5 login
  attempts per 15 minutes per client. After one attack run against the opt-in
  build, a second run cannot log in until the server is restarted.
  `npm run compare` starts fresh servers every time, so it is not affected.
